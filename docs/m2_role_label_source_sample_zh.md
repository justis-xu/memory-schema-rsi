## 对 Graph、Jev、RSI 的约束

当前 `MemoryRecord` 是整条正文加场次元数据；LoCoMo 适配器的 `speaker` 和 `dia_id` 没进入 Mem0 实际提取消息，底层 `attributed_to` 又在项目封装读出时缺失。即使直接透出一个 `assistant`，也无法表达上述跨两人或跨文字/图片渠道的子句。图把整条记忆投射成实体/关系、Jev 只看前 60 字、RSI 用记忆 ID 做经验支持时，都有机会把“存在关联 ID”误当“整个关系由该人原话支持”。这是**数据流风险**；本次没有证明四条已造成具体图边、Jev 决策或答案错误。

## 结论、置信度、下一步优化建议

**结论：** `assistant` 标签在 LoCoMo 能指向有用的第二真人事实，但整条标签不够细。固定 10 条里有 4 条的完整正文至少需要另一说话者或非文字渠道见证；来源核查应落到子句和渠道，不能依赖角色标签做跨基准过滤或直接建边。

**置信度：** 固定 ID 选择、当前库字段、原始 `dia_id`/说话者/query/caption 为高；逐条“哪些子句需要哪些源”是人工保守判断，置信度中高。样本量和每 owner 一条的结构不支持总体频率、自动提取性能或答案收益结论。

**下一步优化建议：** 为待入图/经验的每个事实子句保存多个支持 turn，分别标 `speaker_name`、`source_kind`、`channel` 与 `full/partial/absent`；图片 query 与本人文字要分列。先在这十条及前述 LongMemEval 五条上做离线反伤门，再选择能自动保留这些来源区分的中文提取 POC；不因门控通过就宣称 Graph/Jev/RSI 净收益。
