### `qa233` 的来源记忆其实在历史库中

把“最终槽没目标事实”继续追到记忆版本：历史 ID `663e599c-…` 明写**黛布**与已故妈妈的老朋友重新联系、回忆往事、翻看照片。它在同份无图、融合无 Jev、decider、laya 归档的**其他题**候选池分别出现 20、22、26、26 次；唯独这道 `qa233` 在四臂里既未由向量召回，也未进图候选，更无从进入最终 15 槽。可见这里不是“历史提取器完全漏掉目标事实”，而是**已有事实对这道带错人前提的查询不可达**。上述次数是该 ID 在各归档中的候选出现次数，不是独立样本数或收益率。

Mem0 history 记载该 ID 于 2026-09-25 加入、2026-09-26 删除。当前 Chroma 中另有同义但不同 ID `53330642-…`，history 显示它在 2026-09-26 才加入；不能拿当前 ID 当作 9 月 25 日运行的漏召回证据。历史 ID 已在同批归档的其他题出现，足以证明当时可见；删除原因和当前重建前后的库状态仍未知。机器结果保存这两个正文、事件时间、四份归档的逐题候选命中与文件哈希。

`qa157` 是关键反例：题目有错误所有者，最终第 1 条清楚写了真正所有者，所以“证据充分”可以表示**足以拒绝错误前提**，不必一律给低分。评分契约若不区分“有据回答”和“有据纠错”，只看一个 `sufficient` 数值，会把这两种用途混在一起。上一阶段 RSI 验证器在来源 turn 上也暴露过“有效 ID 不保证人物关系”的问题；它与 Jev 的输入/任务不同，此处只是同一批源话显示的跨组件审计需求，不是把 RSI 误受率转移到 Jev。

## 结论、置信度与下一步优化建议

**结论：** 在 `qa233`，目标关系已写进当时的记忆库，却在四个归档臂的该题候选池中缺席；一次 Jev 停判和一次扩拉都以无关饭局结束。缺口横跨带错人前提的召回、证据识别和答题整合；只调 0.4 阈值无法从这条历史记录证明可救。`qa157` 说明错前提题需要“支持目标事实／支持纠错”分开的标签。`qa111` 保住了正例，但两服务分数分歧不能在缺首判日志时归因。

**置信度：** 旧分数、扩拉标志、最终上下文 ID/正文、答案、中文原始 turn、历史目标 ID 在其他题出现及历史 ADD/DELETE 时间为高；“15 槽没有 `qa233` 目标事件”基于逐条人工语义核查，置信度中；旧首判真实内容、未四舍五入分数、图扩拉新增候选的单次因果贡献、删除原因和该模式总体频率未知。对抗题没有普通金标答案，不能沿用宽松裁判的 exact 标签定义有源正确。

**下一步优化建议：** 新 Jev 留痕已能在未来记录首判/二判实际 state；服务恢复后先预选未参与本次解释的中文关系题，分别标注“能直接回答、能纠正错误前提、缺证据”，核决策分与最终 15 槽是否同层一致，再独立测答题。对 `qa233` 这类错误，优先追目标源 turn→记忆→候选→入槽的哪一层丢失，并保护直接证据；扩拉后若仍无目标人物关系，不应把同话题饭局当替代答案。
