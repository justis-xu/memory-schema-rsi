# 中文 LongMemEval 写入顺序：排除跨日倒序，定位事实来源缺口

2026-09-28。接知识更新五题回源，检查真实适配器与写入方法是否改变场次或消息顺序。范围：中文470题的文件排序，以及固定五题完整历史的离线写入回放。脚本 `scripts/m2_audit_lme_ingest_order.py`；结果 `results/analysis/m2_lme_ingest_order_20260928.json`。

零模型调用、零库/图写入，不初始化Mem0/Chroma；用Recorder承接实际 `EvaluationPipeline.ingest_case`，返回零条记忆。未执行提取、检索、重排、答题。没有更改生产代码或数据顺序。

## 文件排序的实际边界

中文470题中191题有相邻场次的完整时间戳倒序，共2,809个相邻倒序位置；这191题恰为123道 temporal-reasoning 和68道 knowledge-update。**所有倒序均在同一天，跨日倒序为0。** 这里统计的是输入场次相邻排序，不是此前已审的“场次晚于提问时刻”统计。

同日时分在此基准中的严格语义仍未确认，不能把它们自动称为写入错误或未来泄漏。若设计日粒度评测，保持日顺序与场内消息顺序就可能符合意图；若设计时刻粒度在线模拟，应另外明确可见性边界，不能无说明重排或截掉答案。

## 来源并非全部丢失，但事实对齐没有建立

输入backend的messages仅含role/content，metadata有benchmark/case_id/session_id/session_date/user_id；没有显式源消息ID、原始turn位置、纠错关系或每个事实的支持列表。`has_answer`等gold标记没有进入真实调用，这是应保持的边界。

与此同时，原文消息和场内顺序仍在。只要冻结输入文件并记录调用场次、批次消息及日期锚，**可以重建输入来源位置**，不能将缺少显式指针说成输入源话已不可恢复。缺口是从实际输出的每个事实回到一个或多个输入消息的对齐，以及“哪条旧主张被纠正、哪个指标跨场变化、什么值仍适用于历史查询”的关系。

本轮机器结果按答案场次展开消息位置与正文哈希，只用于离线核对。正常运行日志应对所有批次使用同一记录方式，不能依赖answer_session_ids或has_answer来决定哪些消息有来源。

## 结论、置信度、下一步建议

高置信：470题的相邻排序、五题完整232次实际方法调用的场次/消息顺序、输入字段及日期锚。未知：同日时分的benchmark意图、提取器输出关系与当前状态是否正确、中文答题性能。

优化方向据此收窄：

1. 先为新提取增加不含gold的批次来源账：固定数据版本、owner、session、原始消息索引/ID、role、正文与输入哈希。它证明调用看到了哪些源话，但不能将整批消息都当作每个事实的支持。
2. 在这个来源账上，提取输出明确事实级支持消息及模态/范围。确定性校验可检查指针是否属于合法输入；语义支持、同场纠错及历史值保留仍需人工或独立评估，不能用“指针存在”代替正确性。
3. 不为这五题先改时间排序；优先复现工程师的同场纠错、棒球的历史时间窗和雕塑的累计区间。未来模型对照保持源话相同，只改变来源/关系保留方式，另行公布调用上限与反伤。

本阶段排除了一种可能归因并把接口缺口定位到输出事实对齐；没有新增模型成绩，也不代表中文LongMemEval或整体复盘完成。
