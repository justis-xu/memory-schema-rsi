# 签名篮球缺一方：按人物拆问能召回，缓存也有潜在图桥

> 2026-09-26。只研究当前中文无图答错的 `conv-43_qa25`。原问题“蒂姆和约翰拥有什么相似的运动收藏品？”已在 `m2_current_zh_retrieval_probe_zh.md` 核为：蒂姆签名篮球入槽，约翰同事实虽在当前库，却未进向量前 45。本阶段用题面人名构造“约翰有哪些运动收藏品？”和“蒂姆有哪些运动收藏品？”两条子查询；**没有使用金标词“签名篮球”作为查询**。每条一次向量检索及一次重排，零答题/裁判调用。脚本与候选全文：`scripts/m2_probe_signed_ball_paths.py`、`results/analysis/m2_signed_ball_paths_20260926.json`。

| 查询 | 约翰签名篮球记忆 | 蒂姆签名篮球记忆 |
| --- | --- | --- |
| 原问题，单次检索 | 向量前 45 无；最终 15 无 | 向量第 10 → 重排第 4 |

这表明当前缺口不是“约翰事实没写入”，而是**原问题的单次整体向量召回偏向蒂姆**。题面给出两个人，按人物分解后两侧事实均可进入各自的 15 条。下一步若合并候选，必须控制最终仍只有 15 槽、保护两侧直接证据，并检查是否挤走其他必需事实；两次检索的成本也要算入账。当前结果只是候选可达，不是答题收益。

现有 `data/graph_zh/structured_cache.json` 中，蒂姆和约翰两条**当前向量 ID**都含完全同名 `signed basketball` 实体；该实体在缓存中恰连这两条记忆。代码的融合图检索走“种子记忆→关联实体→同实体记忆”，且每节点上限 15，所以若把这两个缓存条目按当前库 ID 正确建进图，蒂姆的入槽记忆提供一条**候选路径**到约翰记忆。不过缓存不是实时 HugeGraph 邻接，也没有验证图服务中对应顶点/边、同用户过滤、最终重排入槽。当前图缓存与中文库总体版本不齐，不能据此宣称现有图已能救这题。

## 本轮库文件哈希异常

探针开始时 Chroma SQLite 文件 SHA-256 与前一阶段一致，结束时字节哈希改变；脚本未调用写记忆接口。随后用只读 SQL 核：embedding 总数仍 **1,995**，各 user 的条数与本轮之前记录一致；前一阶段五题粗排的 **225 次候选记录**逐 ID 检查，均仍存在且正文相同。机器核查：`scripts/m2_audit_signed_ball_integrity.py`、`results/analysis/m2_signed_ball_integrity_20260926.json`。这些检查**不能证明全库逻辑内容完全未变**，也不能确定字节变化是 Chroma 初始化、SQLite 内部页调整还是并行进程所致。后续冻结运行需同时记录文件哈希和全库 ID/内容的逻辑指纹，遇到变动先复核再配对。

**结论：** 对这道中文多实体题，按题面人物拆问无需金标就能分别召回两条必要记忆；当前缓存也显示一个可能的实体桥接，但真实图路径未验证。**置信度：** 两次检索位次、缓存 ID/实体及 225 条旧候选未变为高；活图可达、合并后 15 槽和答案效果未知。**下一步优化建议：** 先做冻结候选的两路合并与一次答题小 POC，记录被挤出的记忆和额外检索成本；若要测图实现，再以当前 ID 重建隔离图并核实体边、候选和最终回答，不复用混版服务图。
