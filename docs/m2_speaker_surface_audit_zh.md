# 说话者名在输入中丢失后，旧记忆与图缓存实际留下多少泛称？

> 2026-09-26。只读复算脚本 `scripts/m2_audit_speaker_surface.py`；逐条泛称记忆及结构缓存条目在 `results/analysis/m2_speaker_surface_20260926.json`。零模型调用。这里核的是**可见词面和潜在图别名**，不是人物错归率。

## 从输入到可见记忆

上一阶段确认：LoCoMo turn 有 `speaker`，但当前 `ingest_case` 只传 `role` 与 `content` 给 Mem0；说话者名并非结构化输入。本阶段去旧中文无图归档中取所有题检索到的记忆，按 ID 去重得 **1,780** 条。正文任何位置出现 `User/Assistant/用户/助手/助理` 等泛称的 **19** 条，其中以泛称开头 **11** 条。泛称集中在 `conv-26/41/43/44/47/48/49`，其余三个对话的检索并集未检出。这说明输入缺名**没有在可见记忆中大量表现为泛称开头**；许多事实显然可由上下文补出人物，但这不证明所有归属都正确。

当前 `data/graph_zh/structured_cache.json` 有 **1,705** 个记忆 ID，和旧归档检索并集重叠 **1,699** 个，版本相近但不完全相同。缓存共有 **4,325** 次实体提及、**901** 次关系提及；精确名为 `User/用户/助理` 等泛称的实体提及 **8** 次，含泛称的关系 **4** 次。这也不是全图节点数或图召回损失率，只是结构提取文本的词面计数。

一个具体的图结构风险在 `conv-41` 可见：与旧归档 ID 对齐的结构缓存分别提到 **John 118 次、约翰 18 次、User 5 次**。其原始 `speaker_a` 是“约翰”；部分英文旧记忆又用 `User` 指代他。`GraphBuilder.build_s1` 的实体键只按 `(user_id, lower(name))` 建立，不做中文名、英文名与 `User` 的别名合并。因此若用这份缓存重建 S1，同一对话中的这三个字符串会成为**不同实体键**，相应事实可能分散在不同节点。用户 ID 作用域仍保留，不会因此把不同对话的 `User` 合成同一节点；尚未证明这种分裂让具体 QA 失分。

## 结论、置信度、下一步优化建议

**结论：** 不传原始说话者名是确定的输入缺口；但旧归档可见记忆中的泛称比例很低（19/1,780 任意位置，11/1,780 开头），不能声称这是当前效果差的主因。更值得追的可验证问题是**同一人物的别名被分成不同图节点**，`conv-41` 的 John／约翰／User 给出了具体入口。

**置信度：** 代码消息构造、旧归档去重计数、缓存词面计数和 S1 键规则为高；缓存与旧归档不完全同版本、检索并集不是完整旧库，所以泛称的历史总量及 QA 净影响未知。`User=约翰` 对上述 `conv-41` 片段有上下文支持，但不能仅凭泛称对整个缓存自动做别名合并。

**下一步优化建议：**

1. 先做不调用模型的**输入契约对照**：给每个 turn 明确传原始 `speaker` 和 `dia_id`，并把历史会话日作为唯一 Observation Date；比较实际 Mem0 提取请求，避免把角色词误当人物名。
2. 对 `conv-41` 的少量 `User`、`John`、`约翰` 相关记忆做来源 turn 核查；只对确有同一人物证据的别名尝试图内归并，并量出关系连通性变化及错误合并风险。不要在所有对话上全局把 `User` 映射为某个人。
3. 固定记忆池和 15 槽预算后，再判断别名修复能否带来**独有且可信的答案证据**；词面节点合并本身不算记忆效果改善。
