## 问题与固定范围

旧来源账的 `batch_id` 是输入内容指纹。同样输入执行两次，或失败后重试，事件里的 `batch_id` 相同；原事件没有运行和尝试身份。后续做中文小提取时，仅靠这个指纹无法区分哪次输出或失败属于哪次尝试。

只为可选来源事件增加调用者提供的 `trace_run_id`、`trace_attempt_id`，分别写在 `batch_input` 和 `batch_outcome` 顶层；不写入输入内容指纹，也不传给 backend。未传参数时保留旧事件格式。非空字符串校验在 backend 调用前完成。调用者必须自行持久化事件、分配稳定且不重复的标识；本阶段没有把 sink 接到现有线上或批量运行脚本。

固定中文 LongMemEval 工程师题 `031748ae`，用真实适配器和空 Recorder 回放同一历史三次：`run-a/first`、`run-a/retry`、`run-b/first`。三次各 **45 批**，backend 请求逐批相同，45 个有序 `batch_id` 相同，输入和结果事件逐批配对，而顶层运行/尝试身份可区分。单元测试 `tests/test_ingest_source_trace.py` 还覆盖空白或非字符串身份在 backend 前拒绝、默认调用兼容、金标隔离和写入失败边界；本阶段 **10 passed**。

## 顺带发现：当前文件与旧回放并非完全同版

当前中文 LongMemEval 文件的 SHA256 为 `f8af9e1aa5b62cd117249c05575774a0ade69b91c9a3385653d706ebb8129590`，旧来源账记录 `e93bd28549d25ba4092034bfe336a92f5fbce7e17693c5672a5f9d3be0d96f1f`。同一题仍是 45 批，但当前与旧账的有序批次指纹仅 **40/45** 相同；不一致的是第 20、24、30、42、44 批，具体 session ID 和两版批次指纹已在机器结果列出。此前人工核查所用的两处答案源场批次指纹仍相同。

这说明当前整文件不能冒充 2026-09-28 的冻结输入，也不能把这次运行称为旧 45 批的精确复现。批次指纹变化表明相关请求内容或批次元数据不同；本阶段没有旧版完整原文件，无法判定是哪段文字改变、为何改变或是否影响其他题。旧报告及其当时的批次账保留，不用当前文件覆盖。

## 结论、置信度、下一步优化建议

**结论：** 可选事件现在能在相同 `batch_id` 下区分调用者标明的运行和尝试；固定 45 批三次回放证明 backend 请求及内容指纹不受身份字段影响。当前中文源文件已有可测版本差异，这道题有 5 批不再与旧归档一致，但两个答案源场保持一致。

**置信度：** 接口行为、Recorder 请求对照、当前/旧批次指纹和单元测试为高。版本差异的具体内容和成因未知；未检全 470 题的漂移范围，也没有真实提取输出、逐事实语义支持或答题收益。

**下一步优化建议：** 真正运行提取时，先冻结源文件 SHA、调用者唯一运行/尝试身份、事件落盘位置及输出原文；发现源文件版本不同则不要混用旧人工标签。再对工程师同场纠错与网球星期精度做少量中文提取，逐子句验收来源、历史值、限定语和无源加强；答题效果需另设同条件配对与反伤检查。
