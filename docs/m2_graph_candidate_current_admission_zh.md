# 历史图候选迁入当前中文库的准入边界

## 问题与范围

前几阶段发现旧图可能召回已删除ID，但尚未量化真实历史候选与当前源库的版本差异。本阶段问：如果用当前源ID/正文作为候选准入依据，会拒绝哪些历史候选？能否仅靠相同正文迁移旧关系？

选择一份确定的历史中文融合运行 `results_zh/zhfull_fused_locomo_20260925_172126.jsonl`，全部已保存1,980题，包含adversarial；与当前只读SQLite的1,995条Memory对齐。当前主轨道为10user/1,800条，另一user的195条不能跨owner匹配。

这是一份**跨版本迁移审计**，不是判断候选在2026-09-25答题时有效与否，不是检查线上当前图。零模型调用、零真实库写入。脚本 `scripts/m2_audit_graph_candidate_current_admission.py`；逐ID哈希、曝光次数、入槽case、同正文当前ID及源指纹见 `results/analysis/m2_graph_candidate_current_admission_20260928.json`。

## 方法

每条归档graph_memories按其case的metadata.user_id查当前完整源清单，分类：当前无ID、owner不符、同ID正文变更、同owner/ID/正文。case owner另与case_id对话名一致性断言。记录graph_context_ids指定的最终选入。

对当前无ID者，再按同owner精确正文查询所有当前ID。精确匹配只为定位，未把这些ID自动替换回旧图。当前SQLite前后逻辑指纹一致。

## 结论、置信度和限制

- **高置信度，所选归档与当前源范围：** 旧候选身份在6个对话中整体不适配当前清单，直接使用旧图或旧归档回填将混用版本。前阶段内特conv-42的断点不是唯一发生身份变化的对话。
- **高置信度，精确字符串范围：** 单靠相同正文自动换ID无法迁移绝大多数旧候选；必须核当前关系来源或重建派生图。
- **未知：** 身份更新的实际操作与时间、历史时刻合法性、当前实时图候选和损失、事实保留比例。缺同期完整源快照、提取输入输出映射、图边版本与变更事件。
- 不能把当前无ID标成历史“脏候选”，不能据1,856次当前拒绝就估计过滤的答题收益；本轮没有重新重排、补位或作答，也不能说拒绝后仅剩912次图入槽。
- 当前没有线上图快照，不能声称当前真实图一定含这936个旧ID；本轮只是给旧图复用设置证据边界。

## 下一步优化建议

1. 当前运行只接纳能精确核当前owner/ID/正文的候选，并归档拒绝原因。对同ID变正文者，应拒绝旧关系依据并重建，而不只换正文继续沿旧边召回。
2. 这6个对话需要当前源版本的关系重建/验证；4个同ID对话也需图版本清单，不能靠候选重合直接发布“版本一致”。
3. 源ID缺失时拒绝当前候选是身份防线，不能用于给历史答案重新评分。任何当前优化实验须两臂都使用当前源清单与相同预算，保存完整候选和版本。
4. 下一阶段将候选准入实现为可单独调用、可留痕的运行接口，并用真实当前源清单保护合法池外候选；旧历史候选只作为版本控制材料。随后回到来源关系提取与中文净收益实验，不以迁移统计代替整体Graph/Jev/RSI复盘。
